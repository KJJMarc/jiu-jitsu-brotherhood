# Jiu Jitsu Brotherhood rebuild: Stage 7 technical architecture and Cursor build brief

Approved working specification, 16 September 2026.

## Objective

Build a new content-led Jiu Jitsu Brotherhood website using the proven operational approach from Kingston Jiu Jitsu:

- Next.js and TypeScript;
- Vercel hosting;
- Supabase for PostgreSQL, admin authentication and media storage;
- Mollie for UK shop payments;
- a custom admin area;
- no Shopify dependency after cutover.

This is a substantial rebuild, not a reskin or a direct translation of the Shopify theme. The new system must preserve the approved content, URLs and catalogue decisions from Stages 1–6 while replacing Shopify's store-first structure.

## System architecture

### Public application

Use the Next.js App Router with strict TypeScript. Prefer React Server Components for content and catalogue rendering. Use client components only where interaction requires them, including menus, search controls, filters, basket state, rich editors and checkout controls.

Public concerns:

- editorial pages, Articles and Techniques;
- server-rendered category and archive pages;
- search;
- lead-magnet and contact forms;
- physical-product catalogue and basket;
- guest checkout and order confirmation;
- redirects, SEO metadata, sitemap and structured data.

### Admin application

Keep the admin area in the same repository under `/admin`, protected by Supabase Auth and server-side authorisation. It should reuse the proven KJJ admin patterns where possible while retaining a separate JJB database and deployment.

Admin concerns:

- Articles and Techniques;
- pages and modular sections;
- categories and tags;
- media and alt text;
- authors;
- physical products, variants, images and inventory;
- draft event-product records;
- orders, payment state and fulfilment;
- navigation, redirects and site settings;
- lead resources and form submissions;
- SEO previews and publication controls;
- audit history.

### Data and services

| Concern | Service |
| --- | --- |
| Relational data | Supabase PostgreSQL |
| Admin identity | Supabase Auth |
| Uploaded images/files | Supabase Storage |
| Payments | Mollie Payments API and verified webhooks |
| Hosting and scheduled jobs | Vercel |
| Transactional email | Provider adapter; choose the existing approved provider during implementation |
| Marketing sign-up | Provider adapter; do not hard-code a specific mailing platform before confirmation |
| Analytics | GA4 or the approved replacement, loaded only after required consent |
| Error monitoring | Optional provider adapter, disabled until configured |

Do not give the browser direct privileged database or payment access. Sensitive mutations occur through authenticated server actions or route handlers.

## Database conventions

- UUID primary keys generated by PostgreSQL.
- `created_at` and `updated_at` as timezone-aware timestamps.
- `published_at` nullable for publishable records.
- `status` enums or constrained text with explicit allowed values.
- Unique, lowercase slugs enforced at the database level within the relevant route namespace.
- Soft archive fields for recoverable records; do not use destructive deletion for products, content, orders or redirects.
- Preserve Shopify IDs and legacy URLs in dedicated migration-reference fields, not in public-facing content.
- Store monetary amounts as integer minor units, for example pence, with currency `GBP`.
- Validate all JSONB structures with shared Zod schemas at application boundaries.

## Core data model

### Admin users

#### `admin_profiles`

| Field | Notes |
| --- | --- |
| `id` | Matches Supabase Auth user ID |
| `email` | Unique |
| `display_name` | Required |
| `role` | Initially `owner`, `editor` or `shop_admin` |
| `is_active` | Revocable access |
| timestamps | Standard |

Authentication alone is not authorisation. Every admin request must confirm an active profile and the required role.

### Authors

#### `authors`

Fields: `id`, `name`, `slug`, `bio`, `credentials`, `avatar_media_id`, `website_url`, `social_links`, `is_active`, timestamps.

Replace the generic migrated `JJB Admin` by assigning real authors during editorial review where known. Do not fabricate authorship.

### Editorial content

#### `content_items`

| Field | Notes |
| --- | --- |
| `id` | UUID |
| `content_type` | `article` or `technique` |
| `status` | `draft`, `published`, `archived` |
| `title` | Required |
| `slug` | Unique within `content_type` |
| `summary` | Card excerpt/standfirst |
| `body_html` | Canonical server-sanitised rich content |
| `primary_category_id` | Required before publication |
| `author_id` | Nullable only while migration review is incomplete |
| `featured_media_id` | Required before publication unless explicitly waived |
| `video_url` | Techniques or video-led articles only |
| `video_provider` | Restricted provider value |
| `duration_seconds` | Optional |
| `original_published_at` | Preserved Shopify date |
| `published_at` | Current publication state |
| `modified_at` | Genuine editorial changes only |
| `seo_title`, `seo_description` | Editable |
| `canonical_override` | Rare, reviewed use only |
| `legacy_shopify_id`, `legacy_url` | Migration reference |
| timestamps | Standard |

Use sanitised HTML as the single rich-body representation so migrated content and the admin editor do not create competing sources of truth. The editor may produce HTML, but saving and rendering must pass through the same allow-list sanitizer.

#### `content_categories`

Fields: `id`, `content_type`, `name`, `slug`, `description`, `sort_order`, `is_active`, SEO fields, timestamps.

Seed only the approved Stage 3 categories. `Past Events archive` is not an ordinary Article category in public navigation; its records migrate into the events model.

#### `tags`

Fields: `id`, `name`, `slug`, `tag_group`, timestamps.

#### `content_item_tags`

Join table with unique `(content_item_id, tag_id)`.

#### `content_relations`

Fields: `source_content_id`, `target_content_id`, `relation_type`, `sort_order`. Use for curated related content, series and previous/next relationships.

### Pages

#### `pages`

Fields: `id`, `page_type`, `title`, `slug`, `status`, `standfirst`, `sections` JSONB, `featured_media_id`, SEO fields, `published_at`, timestamps.

Use validated modular sections from an explicit component registry. Unknown section types must fail validation rather than render arbitrary code. Policy pages may use a simpler rich-body field if this produces a better editing experience.

### Past Events

#### `events_archive`

Fields: `id`, `title`, `slug`, `status`, `start_date`, `end_date`, `location_name`, `location_text`, `summary`, `body_html`, `featured_media_id`, SEO fields, legacy references, timestamps.

#### `event_media`

Ordered join between an event and media records, with optional caption and credit.

There is no required relationship between an event archive record and an event-ticket product draft.

### Media

#### `media_assets`

Fields: `id`, `storage_path`, `public_url` or derived storage reference, `media_type`, `mime_type`, `width`, `height`, `file_size`, `alt_text`, `caption`, `credit`, `source_url`, `source_shopify_id`, `checksum`, timestamps.

- Keep original source references for migration audit.
- Generate responsive delivery variants at render time rather than storing many unexplained duplicates.
- Publication validation should warn when meaningful images lack alt text.
- Reject executable uploads and enforce MIME type and size restrictions server-side.

### Shop catalogue

#### `shop_categories`

Seed exactly six public categories: Gis, Rashguards, T-Shirts & Hoodies, Grappling Gear, Belts and Patches.

Fields: `id`, `name`, `slug`, `description`, `sort_order`, `is_active`, SEO fields, timestamps.

#### `products`

| Field | Notes |
| --- | --- |
| `id` | UUID |
| `status` | `draft`, `active`, `archived` |
| `product_kind` | `physical` or `event_draft`; only `physical` can publish |
| `title`, `slug` | Required; slug unique |
| `description_html` | Sanitised |
| `category_id` | Required for publishable physical products |
| `vendor` | Optional |
| `shipping_required` | Must be true for public launch products |
| `taxable` | Explicitly reviewed |
| `featured_media_id` | Optional in draft, required when published |
| `seo_title`, `seo_description` | Editable |
| `stock_review_required` | True after migration until confirmed |
| `legacy_shopify_id`, `legacy_url` | Migration reference |
| timestamps | Standard |

A database constraint or equivalent server invariant must prevent `event_draft` products from becoming public without an explicit future migration/change.

#### `product_variants`

Fields: `id`, `product_id`, `title`, `sku`, `option_values` JSONB, `price_minor`, `currency`, `stock_quantity`, `allow_backorder`, `weight_grams`, `status`, legacy IDs, timestamps.

- Currency is `GBP` at launch.
- SKU may be temporarily nullable during migration review, but publication validation should require one where operationally appropriate.
- Stock may never be negative unless a deliberate future backorder feature is introduced.

#### `product_media`

Ordered join with alt text override where needed.

#### `inventory_movements`

Fields: `id`, `variant_id`, `quantity_delta`, `reason`, `reference_type`, `reference_id`, `note`, `created_by`, `created_at`.

Stock adjustments must create movements in the same transaction. Do not directly edit stock without history.

### Basket, orders and payments

The browser basket may be stored locally for convenience, but product names, prices, availability and shipping eligibility must be revalidated server-side at checkout.

#### `orders`

Fields include:

- internal UUID and human-readable order number;
- `status`: `pending`, `paid`, `payment_failed`, `cancelled`, `refunded`, `partially_refunded`, `fulfilled`;
- guest name, email and phone where required;
- billing and shipping address snapshots;
- subtotal, discount, shipping, tax and total in integer minor units;
- currency;
- payment provider and provider-payment ID;
- fulfilment status and timestamps;
- source and audit timestamps.

#### `order_items`

Snapshot product ID, variant ID, title, option text, SKU, quantity, unit price, tax treatment and line total. Historical orders must not change when catalogue records change later.

#### `inventory_reservations`

Fields: order, variant, quantity, expiry and status. Create reservations transactionally before sending the customer to Mollie. Release expired or failed reservations through an idempotent scheduled job. Convert reservations into permanent stock movements only once payment is confirmed.

#### `payment_events`

Store provider event ID or deterministic idempotency key, order ID, event type, verified payload summary, processing result and timestamp. Avoid storing unnecessary payment data.

### Discounts

Scaffold but do not activate:

#### `discount_rules`

Fields: `id`, `code`, `name`, `status`, `discount_type`, `value`, `eligibility` JSONB, usage limits, start/end dates and timestamps.

No discount rule is active at launch. The future military discount requires a separate eligibility decision, admin workflow, test plan and publication approval. Mollie receives the final validated amount; it does not own JJB's discount logic.

### Forms and lead resources

#### `lead_resources`

Seed the two approved resources with title, slug, status, description, media, delivery configuration and SEO.

#### `form_submissions`

Store only necessary operational fields: form type, email/name where supplied, consent text/version, provider result, source page, spam score, timestamp and retention state. Do not store sensitive free text beyond the contact message required to answer an enquiry.

Contact and sign-up endpoints require rate limiting, bot protection, server validation and neutral error responses.

### Redirects and site configuration

#### `redirects`

Fields: `id`, `source_path`, optional query matcher, `destination_url`, `status_code`, `is_active`, `notes`, legacy ID, timestamps.

- Allowed status codes: `301`, `308`, `404`, `410`.
- Enforce unique active source matchers.
- Prevent self-redirects and known loops before save.
- Query-aware matching is required for the seven legacy query-string sources.

#### `site_settings`

Typed keys for contact details, social links, announcement content, default SEO, shop availability and operational flags. Secrets never belong here.

#### `navigation_items`

Fields: menu location, parent, label, URL/reference, sort order, visibility and open-in-new-tab. Validate internal references before publication.

#### `admin_audit_log`

Record actor, action, entity type/ID, minimal before/after summary, request correlation ID and timestamp for sensitive admin changes.

## Database security

- Enable Row Level Security on every application table.
- Public anonymous reads are limited to explicitly published content and active physical products.
- Draft content, orders, submissions, audit logs and inventory history must not be anonymously readable.
- Admin mutations require authenticated active roles and should normally pass through server-side operations.
- The Supabase service-role key is server-only and must never use a public prefix or reach a client bundle.
- Storage buckets separate public published media from private migration/import files where necessary.
- Do not expose raw Shopify exports through public storage.

Add automated tests proving that anonymous users cannot read drafts, event products, order data, contact submissions or admin tables.

## Publishing workflow

Every publishable record supports draft and published states. Publication validation must check:

- required title, slug and summary;
- valid category where applicable;
- sanitised body/description;
- required image and useful alt text where applicable;
- valid SEO title and description, with warnings rather than arbitrary truncation;
- no broken internal references;
- product stock review completed;
- product variants, price, UK shipping and tax settings reviewed;
- event-product drafts blocked;
- canonical route not occupied by another record or redirect.

Provide preview links protected from indexing. Preview content must send `noindex` and must not enter public search or sitemaps.

## Search architecture

Start with PostgreSQL full-text search across published Articles, Techniques, public pages and active products.

- Weight title and summary above body text.
- Store or derive a search vector and index it.
- Filter by content type and approved category.
- Return only publicly accessible records.
- Support tolerant prefix matching without returning an unbounded dataset.
- Track search queries only in aggregate and without unnecessary personal data.

Do not add an external search service unless measured scale or relevance problems justify it.

## Mollie checkout architecture

1. The browser submits product/variant IDs and quantities, never trusted prices.
2. The server reloads products and variants, validates that they are active physical products, checks UK shipping and calculates totals.
3. In one database transaction, create the pending order, item snapshots and inventory reservations.
4. Create a Mollie payment using the order's final amount and an idempotency key.
5. Save the Mollie payment ID and return the hosted checkout URL.
6. Mollie redirects the customer to an order-result route that does not itself mark the order paid.
7. A verified webhook retrieves or validates the payment state server-side and processes it idempotently.
8. On confirmed payment, mark the order paid, convert reservations into inventory movements and send confirmation.
9. On failure, cancellation or expiry, release reservations safely.

Requirements:

- Never trust the return redirect as proof of payment.
- Repeated webhooks must not duplicate stock movements or email.
- Log payment transitions without logging secrets or full sensitive payloads.
- Use test credentials outside production.
- Require an explicit production flag before live checkout can be enabled.
- Keep `PAYMENTS_ENABLED=false` until a live end-to-end test is deliberately approved.

## Shipping, tax and fulfilment

- Accept UK shipping addresses only at launch.
- Reject unsupported countries server-side, not just in the form UI.
- Maintain shipping methods and thresholds in validated configuration or tables.
- Calculate shipping before creating the Mollie payment.
- Review tax flags for every retained product before publication.
- Admins can add fulfilment notes and mark paid orders fulfilled; every change is audited.
- Refund state must be reconciled with Mollie rather than changed as a display-only admin toggle.

## Email and privacy

- Use an adapter interface for transactional and marketing providers.
- Order email and marketing consent are separate concerns.
- A purchase must not silently subscribe a customer to marketing.
- Store the exact consent wording/version used by lead forms.
- The two free-resource forms need accessible success and failure states, without standalone legacy thank-you pages.
- Keep secrets and provider list IDs in environment variables.
- Define and document retention for contact submissions, failed checkouts and operational logs.

## SEO implementation

Stage 5 is authoritative. Implement:

- canonical metadata from one shared SEO utility;
- Article, Product, Breadcrumb and Organization JSON-LD builders with tests;
- generated sitemap containing canonical `200` URLs only;
- robots rules that exclude admin, previews, checkout internals and result routes;
- one-hop legacy redirect resolver, including query-aware rules;
- explicit 404 and 410 responses;
- preserved original publication dates;
- Open Graph and social metadata;
- stable image URLs or deliberate migrated replacements.

Redirects should be generated from a machine-readable manifest and validated in CI. Do not maintain independent, drifting copies in middleware, database seeds and framework configuration.

## Migration tooling

The Shopify export and audit files are read-only source material. Migration tooling must be repeatable, idempotent and safe to run in dry-run mode.

### Required commands

Implement equivalent scripts for:

1. `audit-source`: validate files, counts and required fields.
2. `transform-content`: sanitise HTML, rewrite media/internal links and apply Stage 3 categories.
3. `transform-catalogue`: apply Stage 4 product/category outcomes.
4. `import-media`: download, checksum, upload and map media without creating duplicates.
5. `import-data`: upsert transformed records using stable source IDs.
6. `generate-redirects`: combine current Shopify URLs, the 289 existing redirects and Stage 5 decisions into one manifest.
7. `verify-migration`: compare source and destination counts, states, links and media.

Each command should support `--dry-run`, structured output and non-zero exit codes on validation failure.

### Staging and provenance

Use local transformation files or private staging tables. Preserve:

- source filename;
- Shopify GraphQL ID;
- original URL;
- source checksum;
- transformation version;
- import timestamp;
- resulting database ID;
- warnings and manual-review flags.

Never mutate source exports. Do not copy Shopify scripts, PageFly markup, tracking fragments, account widgets or buy-button code into the new content.

### HTML transformation

- Strip scripts, inline event handlers, forms and unsafe embeds.
- Retain supported headings, paragraphs, lists, tables, blockquotes, links and images.
- Convert YouTube embeds to the native responsive media component.
- Rewrite internal Shopify links to final canonical routes.
- Preserve external links with appropriate attributes.
- Identify broken images and unsupported markup for manual review.
- Avoid reformatting text content simply because the HTML is old.

### Exact reconciliation gates

The migrated result must reconcile to:

- 183 source editorial records: 120 ordinary Articles, two event-archive Articles, 60 published Techniques and one draft Technique;
- 35 Shopify product records: 26 retained physical products, five removed products and four retained event-product drafts;
- 289 existing redirect records, each with one deterministic final outcome;
- 30 Shopify pages, each accounted for by Stage 2 and Stage 5;
- all selected media linked or explicitly flagged for review.

The import fails rather than silently skipping a record.

Expected environment-variable groups include:

- server-only Supabase service role;
- Mollie test/live key and webhook configuration;

- analytics IDs and consent controls;
- bot protection and rate-limit configuration;
- operational feature flags.

Maintain `.env.example` with names and descriptions only. Validate required environment variables at startup and fail clearly when a server-only value is accidentally exposed as public.

At minimum:

- `SHOP_ENABLED`
- `CHECKOUT_ENABLED`
- `PAYMENTS_ENABLED`
- `LEAD_FORMS_ENABLED`
- `MILITARY_DISCOUNT_ENABLED`, default false

## Deployment and cutover

1. Build against fixtures and seed data.
2. Provision separate Supabase and Vercel environments.
3. Run a dry-run migration and resolve every warning.
4. Import into preview and complete content, responsive, accessibility and checkout QA.
5. Run a full redirect crawl against preview.
6. Freeze Shopify editorial/catalogue changes or record a defined final delta window.
7. Run the final idempotent import and reconciliation report.
8. Deploy production with checkout disabled.
9. Verify canonical host, sitemap, redirects, forms, media and public read policies.
10. Enable the public shop, then checkout, then live payments as separate controlled steps.
11. Complete one low-value live payment, webhook, stock and refund test.
12. Submit the sitemap and monitor errors.
13. Keep Shopify recoverable until the new system has passed the agreed stability period.

Prepare a rollback plan before DNS or canonical changes. A failed deployment must not require rebuilding the Shopify store from memory.

## Cursor execution rules

Cursor should follow these rules throughout the build:

1. Inspect the existing repository before proposing architecture or writing code.
2. Reuse sound KJJ patterns, but do not couple the two sites or share production databases.
3. Work in small phases with a stated objective, changed files, migrations, tests and rollback notes.
4. Do not edit production data or enable live payment features without explicit approval.
5. Do not guess missing credentials, copy or policy text.
6. Do not create digital products, course access, customer accounts or public event products.
7. Preserve unrelated existing work and never use destructive Git/database commands casually.
8. Use migrations for schema changes and commit generated types where the project convention requires them.
9. Include loading, empty, error and success states rather than implementing only the happy path.
10. Stop after each phase and provide verification evidence before continuing.

## Stage 7 acceptance criteria

- The architecture supports the approved content hierarchy and visual templates.
- Database models account for all migrated content, pages, products, events and redirects.
- Drafts are excluded at the query and policy layers.
- The public shop is physical-only, guest-only and UK-only.
- Mollie payment state and inventory changes are webhook-driven and idempotent.
- Discounts are scaffolded but inactive.
- Migration is repeatable, dry-runnable and exactly reconciled.
- Admin access, RLS, secrets and audit requirements are explicit.
- Cursor has a phased brief with stop points and verification gates.
- Production cutover cannot silently enable live payments or retire Shopify prematurely.
